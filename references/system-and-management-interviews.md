# 系统设计与管理层面试框架

## 适用性判断

- 当 JD 涉及后端、平台、基础设施、数据、AI/ML 平台、分布式系统、集成、架构、扩展性、可靠性、安全或技术负责人职责时，生成系统设计专项。
- 系统设计专项默认生成 2–3 道题。每道题必须直接对应一个或多个 JD 证据 ID；不要仅因职位名称含“工程师”就生成通用题。
- 若材料没有足够信号，写明 `[推断｜依据：现有 JD 未体现系统设计职责] 不适用`。仅当用户明确要求额外练习时，才提供迁移型题目，并标记为 `[建议]`，不得称为高概率面试题。
- 管理层面试专项默认适用于完整面试准备报告。根据岗位级别、业务目标、协作对象和管理范围调整问题，不要把“管理层面试”误写成“候选人一定管理人员”。

## 系统设计：题目选择

从 JD 的业务对象和非功能要求反推题目，优先覆盖最能区分候选人能力的 2–3 类：

1. 核心产品或业务流程：例如订单、消息、搜索、权限、内容分发、支付或工作流。
2. 岗位特定平台能力：例如数据管道、模型服务、观测平台、开发者平台、集成网关或多租户 SaaS。
3. JD 明示的质量属性：例如高可用、低延迟、一致性、成本、安全、合规、全球化或灾备。

每道题先写 `[推断｜依据：JD-xx]`，解释为何可能被问。不得声称这是公司的真实面试题或现有架构。

## 系统设计：每题输出结构

### 1. 题目与边界

- 题目、面试官意图和 JD 依据。
- 3–6 个澄清问题，覆盖用户、流量、功能范围、SLO、数据一致性、安全或合规。
- 明确功能需求、非功能需求和不做事项。

### 2. 假设与估算

- 只使用 JD 已给数字或显式写为 `[假设]` 的练习数字。
- 给出关键容量估算的公式、数量级和设计影响；不要制造公司的真实流量、成本或 SLO。

### 3. 方案

- API 或事件契约、核心数据模型、组件职责和端到端请求/数据流。
- 用纯文本流程、表格或内联 SVG 给出一个紧凑架构图；自包含 HTML 不依赖 Mermaid、CDN 或远程脚本。
- 选择 1–2 个与 JD 最相关的部分深入，例如分区、缓存、索引、队列、幂等、一致性、模型服务或多租户隔离。

### 4. 质量属性与取舍

- 覆盖容量与扩展、可靠性与降级、可观测性、安全与隐私、成本；不相关项可以说明不适用。
- 至少比较一个备选方案，写出选择标准、放弃内容和触发重新设计的阈值。
- 列出 2–4 个故障场景及检测、缓解和恢复路径。

### 5. 面试表达

- 给出 8–12 分钟讲解顺序、2–4 个追问和一份自检清单。
- 方案属于知识型练习时标记 `[建议]` 或 `[知识型参考]`；只有简历证据支持时才能关联为个人经验。
- 简历缺乏对应经验时，给出诚实边界表达，不把练习方案写成生产经历。

## 管理层面试：问题选择

默认生成 6–8 道高价值问题，并按以下维度选择，不为凑数平均覆盖：

- 业务结果与岗位动机：为什么现在选择该岗位，如何理解成功标准。
- 优先级与判断：资源有限、目标冲突或信息不完整时如何决策。
- 主人翁意识与执行：如何推动结果、识别风险、升级问题并完成闭环。
- 跨团队影响力：如何处理分歧、建立信任并让非直属团队协作。
- 失败、反馈与成长：如何面对失误、负面反馈和能力缺口。
- 领导潜力：如何提高团队杠杆、辅导他人或形成机制。
- 人员管理：仅在 JD 或简历表明管理职责时加入招聘、授权、绩效、低绩效、团队设计和继任问题。

## 管理层面试：每题输出结构

- 问题、优先级、管理层关注点和依据；关注点通常是 `[推断]`。
- 回答方案：用“结论—证据故事—关键判断—结果—复盘—岗位连接”组织，而不是编造一段完美答案。
- 推荐故事与证据 ID；无合适故事时写 `[待确认]`，并列出候选人需要补充的事实。
- 60–120 秒第一人称参考回答：仅在证据足够时生成；证据不足时提供可填充骨架。
- 2–4 个压力追问、回答风险和禁止虚构项。
- 对经理岗位补充“团队机制与公平性”检查：说明判断标准、过程一致性、记录方式和对个人的支持，不只给结果。

## 质量检查

- 系统设计题数量为 2–3，或明确标记不适用；每题都有 JD 依据、完整方案、取舍、故障场景和经验边界。
- 所有练习数字都来自 JD 或带 `[假设]` 标签；公司现状、面试安排和内部架构不从题目反推。
- 管理层问题与岗位级别、业务目标或协作范围有明确关系；人员管理题只在材料支持时出现。
- 管理层参考回答不扩大个人贡献；无证据内容保留 `[待确认]`。
- 双语输出保持题意、证据 ID、数字、单位、假设和贡献边界一致，不逐句硬译。
