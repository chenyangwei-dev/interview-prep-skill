## 1. 目标与边界

［目标］在回归耗时和模型成本可控的前提下，尽早发现事实、隐私、语言、结构和整体生成质量下降。

［目标］为每次评测保留可比较的 Skill 版本、案例版本、生成配置、质量结果、Token、成本和延迟。

［边界］确定性规则只能证明已经声明的约束没有回归，不能单独证明报告完整、自然或有面试价值。

［边界］代码覆盖率衡量代码是否被执行，不直接等价于 Skill 输出质量。

## 2. 当前基线

［现状］`evals/cases/` 包含中文后端、英文产品和双语转型三个合成脱敏案例。

［现状］`scripts/eval_report.py` 检查必要证据、未知证据、禁止措辞、数字与证据关联、双语标记、隐私值和待确认项。

［现状］`scripts/validate_report.py` 检查 HTML 结构、必要章节、自包含资源、响应式与打印规则、未替换占位符和危险内容写入方式。

［现状］CI 中的 `--use-samples` 评测固定 `sample_output`，主要验证评分器和案例规则，不会调用修改后的 Skill 重新生成报告。

［缺口］当前 CI 尚不能直接回答“修改后的 Skill 是否让真实生成质量下降”。

［缺口］当前 coverage workflow 会生成覆盖率报告，但未设置覆盖率下降的阻断阈值。

## 3. 目标测试分层

| 层级 | 触发时机 | 内容 | 目标时限 | 是否阻断 PR |
|---|---|---|---:|---|
| ［建议］L0 静态与确定性测试 | 每次 push/PR | Schema、单元测试、HTML 校验、评分器正反例、内置安全样例 | 2 分钟 | 是 |
| ［建议］L1 实际生成冒烟 | 内部分支 PR | 两个代表案例实际生成、HTML 校验、硬性规则评分 | 10 分钟 | 是 |
| ［建议］L2 全量生成回归 | Nightly/手动 | 全部案例、语言和输入格式组合，baseline/candidate 对比 | 60 分钟 | 否，生成报告并告警 |
| ［建议］L3 深度质量评估 | 发布前/每周 | 高风险案例重复生成、成对盲评、人工抽检 | 数小时 | 发布门禁 |

［建议］L1 默认选择中文后端和双语转型案例，分别覆盖中文事实约束与跨语言一致性。

［建议］当修改仅影响英文模板或英文语言策略时，用英文产品案例替换中文后端案例。

## 4. 质量门禁与指标

### 4.1 硬性门禁

［建议］以下指标采用零容忍或 100% 通过，任意一项失败即阻断 L1：

| 指标 | 通过标准 |
|---|---:|
| 案例执行率 | 100% |
| 实际生成成功率 | 100% |
| HTML 校验通过率 | 100% |
| 必要证据召回率 | 100% |
| 未知证据数 | 0 |
| 贡献边界违规数 | 0 |
| 数字、日期、单位不一致数 | 0 |
| 双语关键事实不一致数 | 0 |
| PII 泄露数 | 0 |
| 超过案例上限的待确认项 | 0 |

［建议］硬性门禁保持逐项判定，不把隐私泄露与其他得分做加权平均。

### 4.2 整体质量非劣化

［建议］L2/L3 对 baseline 和 candidate 做隐藏版本身份的成对比较，评价岗位覆盖、个性化、事实一致性、问题深度、答案可用性、缺口诚实度、语言自然度和行动计划可执行性。

［初始建议｜猜测］在缺少历史分布时，先采用以下非劣化阈值：

```text
candidate 胜出或持平案例比例 >= 80%
各质量维度平均下降 <= 0.25 / 5
总体平均分不低于 baseline
事实编造或隐私泄露 = 0
```

［校准要求］积累至少数轮完整回归结果后，根据实际方差、人工一致率和业务容忍度重新设定阈值。

### 4.3 成本与稳定性

［建议］每个真实生成案例记录成功率、重试率、输入/输出 Token、缓存命中、端到端延迟和估算成本。

［初始建议｜猜测］在质量没有显著提高时，可先限制平均成本增长不超过 15%、P95 延迟增长不超过 20%。

［校准要求］成本和延迟预算由实际模型价格、CI 配额和可接受等待时间决定。

## 5. 基线与非确定性控制

［建议］将 `main` 上最近一次通过完整回归的报告和指标保存为 baseline artifact；PR 输出保存为 candidate artifact。

［建议］基线键至少包含：

```text
skill_commit
case_version
input_hash
model
model_parameters
generator_version
evaluator_version
```

［建议］模型、温度、系统配置或评估器版本变化时创建新基线，不跨不兼容配置直接比较分数。

［建议］L1 每个案例只生成一次以控制时长；L3 对事实忠实度、贡献边界和双语一致性等高风险案例重复 2–3 次。

［注意］固定随机种子不能保证所有模型服务完全确定，因此仍需保留重复运行与结果分布。

## 6. 测试选择、缓存与并发

### 6.1 按修改范围选择 L1 案例

| 修改范围 | L1 必跑集合 |
|---|---|
| HTML/CSS 模板 | 对应语言案例、HTML 校验、打印和响应式检查 |
| 证据或贡献规则 | 中文后端、英文产品、双语转型 |
| 语言策略或双语模板 | 英文产品、双语转型 |
| `SKILL.md` 核心生成工作流 | 中文后端、双语转型 |
| 输入提取器 | 对应 PDF/DOCX/Markdown 提取测试和一个实际生成案例 |
| 评分器 | 评分器正反例、全部内置样例；模型生成可交给 Nightly |

［注意］增量选择可能漏掉跨模块影响，因此 Nightly 仍需运行全量集合。

### 6.2 缓存

［建议］缓存标准化输入、baseline 报告、确定性评分结果和不依赖 candidate 的固定资料。

［建议］仅在完整缓存键一致时复用生成结果；Skill commit 或评估器版本变化时禁止错误命中旧缓存。

### 6.3 并发和提前失败

［建议］先执行便宜且确定的 L0；L0 失败时不启动付费生成。

［建议］不同案例并行运行，并通过矩阵并发上限控制模型限流和费用峰值。

［建议］单个案例出现隐私泄露、未知证据或贡献越界时立即标记失败；其他已启动案例继续完成，以保留完整诊断信息。

## 7. CI 工作流设计

### 7.1 `coverage.yml`

［现状］保留现有单元测试、覆盖率、Codecov 上传和内置安全样例评测。

［建议］在获得稳定基线后，为关键脚本增加覆盖率非下降门槛；门槛数值需要用当前 `main` 覆盖率校准。

### 7.2 `regression-smoke.yml`

［建议］触发方式为内部 PR、`workflow_dispatch`，执行 L1 两个实际生成案例。

［建议］输出 `evaluation.json`、`validation.json`、脱敏后的汇总指标和失败原因；最终报告因可能包含简历内容，不默认上传为公开 artifact。

［建议］Job 设置 10 分钟 timeout，并为外部模型调用设置单次超时和有限重试。

### 7.3 `nightly-regression.yml`

［建议］使用 `schedule` 和 `workflow_dispatch`，运行全部案例矩阵、baseline/candidate 对比和成本统计。

［建议］Nightly 失败时创建可追踪告警，但不回写或修改 Skill 源文件。

### 7.4 `release-quality.yml`

［建议］仅手动触发，运行高风险案例的多次生成、成对盲评和人工抽检清单。

［建议］发布门禁同时要求硬性规则通过和质量非劣化通过。

## 8. 结果与数据结构

［建议］每次回归生成统一 `run-summary.json`：

```json
{
  "schema_version": 1,
  "run_id": "...",
  "trigger": "pull_request|nightly|release",
  "skill_commit": "...",
  "baseline_commit": "...",
  "case_version": "...",
  "generator": {
    "model": "...",
    "parameters_hash": "..."
  },
  "execution": {
    "total": 0,
    "completed": 0,
    "failed": 0,
    "duration_ms": 0
  },
  "hard_gates": {
    "passed": false,
    "counts": {}
  },
  "quality": {
    "pairwise_win_or_tie_rate": null,
    "dimension_deltas": {}
  },
  "usage": {
    "input_tokens": null,
    "output_tokens": null,
    "estimated_cost": null,
    "cache_hit_rate": null
  }
}
```

［隐私要求］汇总结果只保存证据 ID、统计值、哈希和错误类别，不保存 JD、简历、完整模型输入或私人联系方式。

## 9. 分阶段实施

### 阶段 A：PR 实际生成冒烟

- [ ] ［任务］为现有案例补充完全脱敏的 JD 和简历输入文件。
- [ ] ［任务］确定 CI 可调用的生成器命令、模型和参数。
- [ ] ［任务］新增 `regression-smoke.yml`，运行中文后端和双语转型案例。
- [ ] ［任务］生成统一 `run-summary.json` 并上传脱敏指标。
- [ ] ［任务］设置 10 分钟任务超时、模型调用超时和有限重试。
- [ ] ［验收］每个 PR 会实际生成报告，而不是只评分固定 `sample_output`。
- [ ] ［验收］任一硬性门禁失败会阻断 PR。

### 阶段 B：Nightly 全量回归

- [ ] ［任务］扩充岗位、语言、文件格式和信息完整度组合。
- [ ] ［任务］保存并版本化 `main` baseline artifact。
- [ ] ［任务］实现案例并行、缓存键和并发上限。
- [ ] ［任务］新增 `nightly-regression.yml` 与失败告警。
- [ ] ［验收］Nightly 能输出逐案例差异、失败类型、Token、成本和延迟。

### 阶段 C：质量非劣化评估

- [ ] ［任务］定义 1–5 分质量维度及评分锚点。
- [ ] ［任务］实现 baseline/candidate 隐藏身份的成对评估。
- [ ] ［任务］建立人工抽检表，记录评估器与人工的一致率。
- [ ] ［任务］用历史运行结果校准 `80%`、`0.25` 等初始阈值。
- [ ] ［验收］发布前能够回答 candidate 在哪些案例和维度上优于、持平或弱于 baseline。

### 阶段 D：可观测性平台接入

- [ ] ［任务］在统一生成适配器边界记录 trace、step、token、cost、latency 和 evaluator 结果。
- [ ] ［任务］默认屏蔽输入正文、简历内容和联系方式。
- [ ] ［任务］评估 Langfuse 或其他平台是否降低排障与分析成本。
- [ ] ［验收］接入平台不会改变生成结果、硬性门禁和本地可运行能力。

## 10. 风险与安全约束

［安全要求］不要使用 `pull_request_target` 执行不受信任的 PR 代码并向其暴露模型密钥。

［建议］外部 fork PR 只运行 L0；需要模型密钥的 L1 由维护者审查后手动触发，或仅对仓库内部受信分支启用。

［安全要求］真实简历不得进入案例库、Git 历史、公开 artifact 或评估日志。

［风险］LLM Judge 可能偏好更长、更流畅或与自身风格相似的答案，因此不能替代硬性事实规则和人工抽检。

［风险］Nightly 的模型或服务端版本变化可能造成与 Skill 修改无关的分数波动；结果必须记录模型和参数版本。

## 12. 完成定义

［完成标准］PR 路径在 10 分钟目标内完成 L0 和 L1，并对事实、隐私、证据、语言和结构回归进行自动阻断。

［完成标准］Nightly 能覆盖完整案例矩阵，并输出 baseline/candidate 差异、成功率、Token、成本和延迟。

［完成标准］发布流程包含质量非劣化结论，且所有阈值都能追溯到配置、历史数据或明确的人工决策。

［完成标准］任何评测和可观测性接入都不把真实简历或私人信息写入公开日志与 artifact。
